1. Introduction
1.1 Purpose
This Software Requirements Specification (SRS) defines the complete functional and non-functional
requirements for SocietyPilot v2.0 — a comprehensive, multi-tenant, cloud-based housing society
management platform built for the Indian market. Version 2.0 significantly expands the original SRS to
include: NestJS as the backend framework, a full React Native mobile application (iOS + Android), a
WhatsApp Bot with conversational flows, a Platform-Level Super Admin Panel (for SocietyPilot owners),
and a Per-Society Admin Panel (for society committees).
1.2 Project Overview
SocietyPilot is a SaaS platform designed to digitise and automate every operational aspect of housing
societies — from maintenance billing and complaint management to vendor directories, amenity
bookings, meeting coordination, security access, and financial reporting. The platform is engineered to
scale from small 30-flat societies to large township societies with 1,500+ flats, multiple towers,
clubhouses, swimming pools, and complex multi-basement parking systems.
ℹ SocietyPilot targets the gap between expensive enterprise tools (ApnaComplex at ₹15,000+/year) and basic
notice apps. It is the first Indian platform architected for large-scale multi-tower societies at an affordable price
point, now with full mobile-first React Native experience and AI-powered WhatsApp Bot.

3. System Architecture
3.1 High-Level Architecture
SocietyPilot v2.0 follows a Modular Monolith architecture on the backend built with NestJS — a single
deployable TypeScript/Node.js application structured into independent, clearly-bounded NestJS modules.
This approach allows a small team to move fast while keeping the codebase organised for future
extraction into microservices if needed.
Request Flow (Web & Mobile):
• Client (React Web / React Native App) → HTTPS → Cloudflare CDN → Railway.app Backend
(NestJS)
• Backend → PostgreSQL (primary data) + Redis (sessions, cache, queues)
• Background workers (BullMQ) → WhatsApp API / SendGrid / MSG91 / Razorpay / Cloudflare R2
Request Flow (WhatsApp Bot):
• User sends WhatsApp message → Meta Cloud API → Webhook → NestJS WhatsApp Bot Module
• Bot Module → parses intent → calls internal service layer → responds via WhatsApp reply
• Complex bot flows (payment, multi-step) → session state stored in Redis
ℹ Architecture Decision: NestJS replaces Express.js in v2.0 for its TypeScript-first design, built-in dependency
injection, Guards for RBAC, Interceptors for logging, Pipes for validation, and its module system that mirrors the
platform's domain boundaries perfectly.
3.2 Multi-Tenant Design
Every society operates as a fully isolated tenant on a single database. The multi-tenancy strategy uses
shared tables with society_id as a mandatory column on every table, combined with PostgreSQL Row-
Level Security (RLS) and NestJS middleware enforcement.
Isolation Rules:
• Every database query is automatically scoped to the authenticated user's society_id via Prisma
middleware
• NestJS custom @SocietyGuard() injects society_id from the JWT token into every request context
• A user from Society A can never read, write, or query data belonging to Society B
• SUPER_ADMIN is the only role that can query across societies using the Platform Admin Panel

Each domain area is a self-contained NestJS module following the standard pattern: Module → Controller

3.4.2 Cross-Cutting Concerns
• @UseGuards(JwtAuthGuard, RolesGuard) — applied globally; roles checked via @Roles() decorator
• SocietyContextInterceptor — injects society_id into every request from JWT; applied globally
• AuditInterceptor — logs every write operation (POST/PATCH/DELETE) to audit_logs table
• ValidationPipe — global pipe; transforms and validates all DTOs via class-validator
• HttpExceptionFilter — global exception filter; standardises error responses
• ThrottlerGuard — rate limiting per IP via @nestjs/throttler; Redis-backed

4.3 RBAC Implementation (NestJS Guards)
NestJS implements RBAC through a chain of Guards that execute in order on every protected request:
• JwtAuthGuard — extends AuthGuard('jwt'); validates token; populates req.user with JWT payload
• RolesGuard — reads @Roles() metadata via Reflector; checks req.user.role against allowed roles
• PermissionsGuard — reads @Permission() metadata; checks req.user.permissions[] array
• SocietyContextGuard — validates societyId in JWT matches resource's society_id; prevents cross-
tenant access
• TowerScopeGuard — if role is TOWER_CAPTAIN, validates resource belongs to user's tower_id

6.5 Conversation Session Management
• Each active conversation tracked in Redis with key: bot:session:{phone_number}
• Session stores: currentFlow, currentStep, collectedData (JSON), lastActivityAt
• Session expires after 10 minutes of inactivity (Redis TTL = 600s)
• On session expiry mid-flow: bot sends 'Your session timed out. Type Menu to start again.'
• Concurrent sessions from same number: last message always wins (new session resets old)
• Language support: English (v1), Hindi (v2) — detected by user's first message language

• Opt-out status stored in bot_opt_ins table; respected by all notification dispatchers

11. API Design Standards
11.1 REST Conventions
• Base URL: https://api.societypilot.in/v1
• All responses: JSON. Content-Type: application/json
• Authentication: Bearer token in Authorization header (all protected routes via JwtAuthGuard)
• society_id injected from JWT via SocietyContextInterceptor — never accepted as query param
• NestJS ValidationPipe enforces DTO validation on all request bodies

Success: { "success": true, "data": { ... }, "meta": { "page": 1, "total": 142 } }

13. Business Rules
13.1 Financial Rules
• A maintenance bill cannot be deleted once generated — only waived with mandatory reason and
Chairman approval
• A confirmed Razorpay payment cannot be deleted — only refunded via separate refund transaction
• Move-out blocked if any maintenance dues are unpaid — system shows exact outstanding amount
• Expense above ₹50,000 requires a meeting resolution vote before Chairman can approve
• Sinking fund balance can never go below ₹0 — system blocks any expense that would result in
negative balance
• Pro-rata billing: if a resident moves in after the 15th, bill is 50% of monthly; before the 15th, full month
13.2 Complaint Rules
• A complaint closed by resident cannot be reopened after 7 days — new complaint must be raised
• Anonymous complaints hidden from Tower Captain — visible only to Secretary, Chairman,
SUPER_ADMIN
• Open with no assignment after 24 hours: auto-escalation fires to Secretary
• Assigned with no update after 48 hours: auto-escalation fires to Chairman
• Committee member cannot close a complaint — only Resident (requestor) or Secretary/Chairman can
close
13.3 Amenity Booking Rules
• Flat with >2 months outstanding dues cannot book paid amenities
• Full refund if cancelled 24+ hours before slot; no refund if cancelled within 24 hours
• Maximum active bookings per flat: configurable per society (default 2 simultaneous)
• Damage deposit refunded only after Facility Manager marks 'No Damage' post-event
• Blackout dates set by committee override all resident bookings — affected residents are notified
13.4 Security Rules
• A visitor on the blacklist triggers automatic WhatsApp alert to Chairman and Security Supervisor —
guard cannot override
• Pre-approvals for domestic workers auto-expire if the flat's resident moves out
• SOS alert sends to all committee members simultaneously — cannot be selectively suppressed
• Visitor approval via WhatsApp Bot: if resident does not respond within 10 minutes, visitor is denied
entry automatically
13.5 Platform Rules (SUPER_ADMIN)
• A society can be suspended for non-payment after 15 days past subscription due date — data retained
for 90 days
• SUPER_ADMIN impersonation sessions are strictly time-limited (30 minutes) and fully audit-logged
• Feature flags changed by SUPER_ADMIN take effect within 60 seconds via Redis pub/sub
